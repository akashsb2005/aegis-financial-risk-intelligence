# AEGIS Relational Schema

## 1. Purpose

This document maps the AEGIS ER model to the implemented PostgreSQL relations. It is based on `database/ddl/01_schema.sql`. PK means primary key, FK means foreign key, UQ means unique constraint, NN means NOT NULL, and CK means CHECK constraint.

## 2. Relational schema notation

- `COMPANIES(company_id PK, company_name NN, registration_number UQ, industry, country, annual_revenue CK, employee_count CK, created_at NN, updated_at NN)`
- `FINANCIAL_RECORDS(financial_record_id PK, company_id FK NN, fiscal_year NN, revenue CK, net_profit, total_assets CK, total_liabilities CK, total_debt CK, shareholders_equity, operating_cash_flow, created_at NN, UQ(company_id, fiscal_year))`
- `ROLES(role_id PK, role_name NN UQ, description, created_at NN)`
- `USERS(user_id PK, role_id FK NN, full_name NN, email NN UQ, password_hash NN, is_active NN, failed_login_attempts NN CK, locked_until, last_login_at, created_at NN, updated_at NN)`
- `USER_SESSIONS(session_id PK, user_id FK NN, token_hash NN UQ, expires_at NN, revoked_at, created_at NN)`
- `PASSWORD_RESET_TOKENS(token_id PK, user_id FK NN, token_hash NN UQ, expires_at NN, used_at, created_at NN)`
- `RISK_ASSESSMENT(risk_assessment_id PK, company_id FK NN, risk_score NN CK, risk_level NN CK, assessed_at NN, model_version, explanation, assessed_by FK NULL)`
- `RISK_ASSESSMENT_AUDIT(audit_id PK, risk_assessment_id NN, company_id NN, risk_score NN CK, logged_at NN, action_type NN CK, risk_level NN CK, model_version, explanation, assessed_by)`

### 3.7 RISK_ASSESSMENT

| Attribute | PostgreSQL type | Constraints / meaning |
|---|---|---|
| risk_assessment_id | integer | PK; generated by sequence |
| company_id | integer | NN; FK to companies; ON DELETE CASCADE |
| risk_score | numeric(5,2) | NN; between 0 and 100 |
| risk_level | varchar(20) | NN; LOW, MEDIUM, HIGH or CRITICAL |
| assessed_at | timestamp | NN; defaults CURRENT_TIMESTAMP |
| model_version | varchar(50) | Nullable |
| explanation | text | Nullable |
| assessed_by | integer | Nullable FK to users; ON DELETE SET NULL |

A BEFORE UPDATE OR DELETE trigger rejects changes to existing assessments. New assessments should be inserted to preserve history.

### 3.8 RISK_ASSESSMENT_AUDIT

| Attribute | PostgreSQL type | Constraints / meaning |
|---|---|---|
| audit_id | integer | PK; generated by sequence |
| risk_assessment_id | integer | NN; copied source identifier; no FK declared |
| company_id | integer | NN; copied company identifier; no FK declared |
| risk_score | numeric | NN; between 0 and 100 |
| logged_at | timestamp | NN; defaults now() |
| action_type | varchar(20) | NN; restricted to INSERT |
| risk_level | varchar(20) | NN; LOW, MEDIUM, HIGH or CRITICAL |
| model_version | varchar(50) | Nullable |
| explanation | text | Nullable |
| assessed_by | integer | Nullable copied identifier; no FK declared |

An AFTER INSERT trigger on `risk_assessment` calls `log_risk_assessment()` to create the snapshot. The current DDL intentionally has no FK constraints on the audit table; do not describe its copied identifiers as enforced foreign keys.

## 4. Foreign-key relationship and delete behavior

| Child relation.column | Parent relation.column | Nullable? | ON DELETE |
|---|---|---:|---|
| financial_records.company_id | companies.company_id | No | CASCADE |
| users.role_id | roles.role_id | No | Default NO ACTION |
| user_sessions.user_id | users.user_id | No | CASCADE |
| password_reset_tokens.user_id | users.user_id | No | CASCADE |
| risk_assessment.company_id | companies.company_id | No | CASCADE |
| risk_assessment.assessed_by | users.user_id | Yes | SET NULL |

No foreign keys are declared on `risk_assessment_audit` in the tracked DDL.

## 5. Keys and uniqueness

| Relation | Primary key | Additional uniqueness |
|---|---|---|
| companies | company_id | registration_number UNIQUE (nullable) |
| financial_records | financial_record_id | (company_id, fiscal_year) |
| roles | role_id | role_name |
| users | user_id | email |
| user_sessions | session_id | token_hash |
| password_reset_tokens | token_id | token_hash |
| risk_assessment | risk_assessment_id | None declared |
| risk_assessment_audit | audit_id | None declared |

The non-null UNIQUE attributes `role_name`, `email`, `token_hash` and the composite key `(company_id, fiscal_year)` are candidate keys in their respective relations. `companies.registration_number` is nullable, so it is not treated as a candidate key without a NOT NULL rule.

## 6. Integrity constraints

- Company revenue and employee count cannot be negative when supplied.
- Financial fiscal year must be at least 1900.
- Financial revenue, assets, liabilities and debt cannot be negative when supplied.
- Failed login attempts cannot be negative.
- Risk score must be within 0–100.
- Risk level must be one of LOW, MEDIUM, HIGH or CRITICAL.
- Audit action type is restricted to INSERT.
- Primary keys, UNIQUE constraints and foreign keys enforce entity and referential integrity.

## 7. Indexes, views, routines and triggers

The tracked DDL defines the index `idx_risk_assessment_company_date` on `risk_assessment(company_id, assessed_at DESC)`.

The view `company_risk_view` joins risk assessments to companies and optionally to the assessing user.

The schema also defines:
- Procedure `add_risk_assessment` to insert a new assessment.
- Function `compute_risk_delta` to calculate a change between the latest and historical score.
- Function `get_company_risk_level` to return the latest risk level.
- Trigger function `log_risk_assessment` and AFTER INSERT trigger `trg_log_risk_assessment`.
- Trigger function `prevent_risk_assessment_modification` and BEFORE UPDATE OR DELETE trigger `trg_prevent_risk_assessment_modification`.

## 8. Implementation boundary

This relational schema documents the tables and constraints present in the tracked DDL. It does not claim that vector-embedding, event/news, evidence-document, or application-layer tables exist. Those components require separate implementation and schema migrations before they can be reported as completed.
